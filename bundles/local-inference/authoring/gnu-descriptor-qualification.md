# GNU descriptor consumer qualification preparation

This unsigned source contract prepares a distinct GNU/tinygrad consumer. It
does not select a product witness, enable a Worker, install a runtime, or
authorize a probe. The existing fixed-namespace GNU qualification remains
specific to its original consumer.

The first feasibility route reuses the exact GNU product bytes beneath the
selected private descriptor root. Execute the independently loadable selected
GNU loader with its exact interpreter and library directory, disabling the
loader cache and supplying an explicit Python home. Keep the exact separately
loaded musl compiler closure. `gpu_bootstrap.descriptor_loader_probe` assembles
this proposal; it never executes it.

The [Linux loader documentation](https://www.man7.org/linux/man-pages/man8/ld-linux.8.html)
describes direct loader invocation and library-path precedence. Inference:
this may avoid the interpreter's fixed PT_INTERP for that invocation. It does
not establish transitive loading, Python startup identity, compiler-child
execution, or compatibility with the actual Modal driver.

Each qualification attempt must bind the admitted verifier, selected GNU
product and its destination-local witness, immutable realization descriptors,
selected compiler/tinygrad source, cleanup contract, device occurrence and
funding owner before contact. A copied source-site qualification is insufficient.

Required checks, in order:

1. Independently verify the selected GNU ELF inventory and regular-file hashes,
   loader independence, DT_NEEDED/symbol-version closure, NODEFLIB and exact
   runtime members. Confirm all bytes and their delivery operation exist.
2. Under the actual proposed launch, verify interpreter and Python prefix,
   safe import paths, native extension origins and every file-backed ELF
   mapping. Include ctypes/libffi and libraries loaded after tinygrad imports.
3. Remove a required provider in a separate bounded negative fixture while an
   ambient candidate exists. Require refusal before backend contact. Inspect
   fixed RUNPATH, cache, default directories, hardware capability directories,
   extension imports and driver dlopen dependencies; selected entry paths alone
   do not prove those searches closed.
4. Invoke the pinned CUDA:PTX path with the selected driver ABI. Record every
   actually loaded provider and whether any CPU compiler runs. Verify each
   required compiler child uses its separately selected musl loader and exact
   support files. Direct GNU invocation does not bypass a child's PT_INTERP.
5. Only after the independently admitted device observer and accounted raw
   device owner are available, measure a small tensor/kernel, exact short and
   task-shaped model requests, memory, numerics and cancellation. Context
   synchronization/destruction and process retirement must join exact owner
   and selected resource-set evidence before release. Unknown driver use
   retains capacity.
6. Retain the independent qualification output on the controller with complete
   input/content/runtime/device identities and contact/accounting evidence.
   Activate only the separately selected consumer relationship that passed.

If a required same-byte dependency cannot be closed, retain its failed probe
and evaluate the existing Lillux namespace path on actual gVisor. If that path
is unsupported, produce and qualify a separate relocatable GNU product on a
supported producer host, with complete destination-local acquisition. These
are finite alternatives, not authority to rewrite the production system.

No selected GNU payload, exact provider driver closure, device observation,
executed probe, or signed descriptor consumer exists in this source preparation.
Synthetic controls establish assembly and refusal behavior only.
